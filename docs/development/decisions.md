# Design Decisions

The design of jl1his-logger, the QSO log of record for JL1HIS, and the reasons behind it, as implemented on 2026-10-25. A change that departs from a decision here, or settles something left open, updates this file in the same change.

## Background

- The log is the single source of truth for contacts. QSOs are entered in the web UI or sent by logging clients through an API, then exported as ADIF and fed to eQSL, LoTW, contest summary sheets, QSL card generation and POTA.
- The application does only what this use needs, with a web UI built for entering and checking QSOs.
- A Wavelog API v2 compatibility layer under `/wl2` once let logging clients written for it log here. It was removed on 2026-10-28 together with its tokens and the Wavelog IDs of Stations (migration 12 deletes them); logging clients use the native API.

## Structure

- A new, separate repository (this one) holding one server, one SQLite database, a same-origin SPA / PWA and a desktop entry client.
- The server is Rust + axum; the client is SvelteKit.
- One SQLite database. Set WAL and `busy_timeout`, and keep write transactions short.
- The CLI does only what the web app and the native API cannot: `migrate`, `setup` (the first admin, see Users and Permissions), `backup` and `restore`. Everything else an admin, owner or operator does is on the web app and the API, and is not repeated in the CLI. Instance-wide key / value settings, which only the CLI wrote and nothing read, were dropped with migration 14.
- The server is one package: no workspace. `domain` stays free of the database, network and file system by convention and review. It is split into a crate of its own only when another binary or repository needs it, or when build times call for it.
- The query syntax of Search is the one shared crate, `query/` beside `server/`: a path dependency of the server, without a workspace, and compiled to WASM with `wasm-bindgen` (its `wasm` feature) for the client. It holds parsing a query and matching a row, with the `call_base` rule matching needs, and nothing else; the server turns the parsed terms into SQL. It has no dependencies outside the `wasm` feature, so no `regex`, and the module is about 70 KB. The client builds it with `wasm-pack` before it builds itself, and loads it asynchronously before the first query.
- The desktop entry client is a Tauri v2 app under `desktop/`: a SvelteKit app built with `adapter-static` like the web client, and its Rust side in `desktop/src-tauri/`, a package of its own outside any workspace. It is an application, not a shared crate. It is a separate app rather than the web client in a window because it does what a browser cannot: it talks to rigctld and listens for other programs on the local machine.

## Required Features

- QSO store, Station Location, Instrument, Logbook, User, Membership, API tokens.
- Write API (create, update, delete), read API (filters and ADIF output), differential fetch, SSE.
- ADIF import (loading existing logs, and merging QSL fields into existing QSOs).
- Confirmation state (paper QSL, eQSL and LoTW held separately).
- Reference data: the CTY archive (cty.dat and cty.csv), installed by an admin; the ADIF tables (bands and frequencies, modes and submodes, QSL values, QSO field names, DXCC entities, subdivisions), built in from the ADIF specification.
- lookup: entity information from cty.dat and previous contacts in the own log (name / grid / QTH).
- Web UI: log list and search, single-QSO editing, Live QSO entry, voice entry, Station Location and Instrument editing, ADIF import and export, bulk QSL state changes.

## Out of Scope

Dashboards, maps, DX cluster, QRZ / HamQTH integration, CAT on the server (the desktop client reads its rig through rigctld for itself; see Desktop Client), contest modules, awards, satellites, themes beyond light and dark, organization hierarchies and fine-grained permissions.

## Decisions

### IDs and Duplicate Detection

- The QSO ID is a client-generated UUID v7. `POST` is idempotent: resending the same ID returns the existing row.
- Heuristic duplicate detection (same call, same band, same mode, compared ignoring case, and `TIME_ON` within 15 minutes) never refuses a record and only warns. It is returned both by the lookup, given the band, mode and time of a QSO being entered, and in the `warnings` of the `POST` response, with the detection shared between them.
- Each Logbook has server-assigned integers `seq` (insertion order) and `updated_seq` (update order). They are never reused, even after deletion.

### Change History

- There is no append-only change log.
- A row carries `updated_seq`, `revision`, `updated_by`, `updated_at` and a deletion tombstone. Tombstones are never removed.
- The cursor generation is held once per Logbook, not on each row; every differential response and SSE event reports it next to `updated_seq`.
- A differential fetch returns the current rows with `updated_seq > N`, deleted ones included (upsert / delete). Intermediate changes and the state at a past moment are not provided.
- Conflicting updates are detected by `revision`.
- Should history become necessary, it can be added later with SQLite triggers that stack the JSON of the row before each update. The shape of the API does not change.

### Own Station Information

- When a QSO is created, the Station's defaults are baked into the row as `STATION_CALLSIGN` / `MY_*`. Editing the Station does not change past ADIF.
- `station_location_id` is held separately for classification and search.
- Past rows are corrected with an explicit bulk update that states the number of affected rows.
- Stations are archived rather than deleted.
- When a QSO is created through the native API, the server fills the `DXCC`, `CQZ`, `ITUZ` and `CONT` the record lacks from the installed `cty` data. Values given are never overwritten, nothing is filled for a kind that is not installed, and editing a QSO later does not fill them again. Reference data that cannot be read is logged and never refuses the QSO. An ADIF import keeps its records as they arrived.
- A Station holds no equipment: `MY_RIG`, `MY_ANTENNA` and `TX_PWR` are refused in its fields and belong to Instruments. A migration removes them from the fields of existing Stations; QSOs keep the values already baked into them.
- The Station editor orders its location fields from the entity down: `MY_DXCC`, `MY_STATE` (whose choices follow it), `MY_CITY`, `MY_CNTY`, `MY_GRIDSQUARE`, then `MY_POTA_REF`. `MY_DXCC` is searched by code or by the English name of the ADIF table; choosing an entity sets the code only. `MY_CQ_ZONE` and `MY_ITU_ZONE` are not filled from it: zones follow the location, and an entity's representative zones are wrong for the entities that span several (United States, Canada, Russia, Brazil, Australia, China), with no table here telling which those are. `MY_GRIDSQUARE` can be filled from the browser's geolocation as a six-character locator; nothing else is taken from the position.

### Instruments

- An Instrument is the equipment of a QSO: a rig, an antenna and a default TX power. It sits above the Station and is independent of it, so any Instrument can be used with any Station of the Logbook. A QSO may have none, and then nothing fills `MY_RIG`, `MY_ANTENNA` or `TX_PWR`.
- A Logbook owns its Instruments, as it owns its Stations. A rig that several Logbooks use is registered in each of them.
- An Instrument has a name, the fixed fields `MY_RIG`, `MY_ANTENNA` and `TX_PWR`, each optional, and a map of other fields like a Station's. The map refuses the fixed fields and `STATION_CALLSIGN`; it may hold keys a Station also holds, and the Instrument's value then wins. A rig whose power or antenna differs by band is registered as one Instrument per band.
- `TX_PWR` is a decimal number of watts greater than zero, with at most six decimal places (`0.5`, `5`, `100`), so QRP and QRPP powers can be written; anything else is refused. It is stored as given.
- The `_INTL` fields are not used. ADIF can write them only in ADX, so `MY_RIG` and `MY_ANTENNA` carry text outside ASCII as the other fields already do.
- When a QSO is created, the given fields win, then the Instrument's values, then the Station's, then the default `OPERATOR`; each fills only what is still absent. `instrument_id` is held on the QSO next to `station_id` for classification and search, and is `NULL` without an Instrument.
- Editing an Instrument does not change past QSOs, and changing a QSO's Instrument does not bake its values in again. Past rows are corrected with an explicit rewrite that states the number of affected rows (see Bulk Changes).
- A Logbook may name an area code field: the ADIF field that holds the regional code of the other station, with the label the screens show for it (`area_field` and `area_label` on the Logbook; `CNTY` labelled "JCC / JCG" in Japan, `CNTY` labelled "County" in the US, `STATE`, or none). Owners set it with `PUT /api/logbooks/{id}/settings` (`{ "name", "area_field": { "name", "label" } | null }`), which also renames the Logbook. The name is any ADIF QSO field or `APP_*` field except the required fields (`CALL`, `QSO_DATE`, `TIME_ON`, `BAND`, `MODE`), `STATION_CALLSIGN`, `OPERATOR` and `MY_*`; the client also keeps the fields that have their own place on the screens out of it. Changing the field moves no recorded values. Nothing is Japan-specific by default: a new Logbook has no area code field, and JCC / JCG is a setting.
- Instruments are archived rather than deleted. As for Stations, archiving only takes an Instrument out of the client's choices.

### Favorites

- Each member marks Stations and Instruments of a Logbook as favorites of their own. A favorite is a preference of one User in one Logbook, not a property of the Station or Instrument: it is a row of `station_favorites` or `instrument_favorites`, marking one leaves `updated_at` alone, and other members do not see it.
- Every member may mark any Station or Instrument, though only owners edit Stations. An API token marks and sees the favorites of the User it belongs to, so a desktop entry client lists them as its user's web client does. Removing a Membership removes that member's favorites.
- `GET /stations` and `GET /instruments` return `favorite` for the caller and list favorites first among the active ones, then the others by name, then the archived ones. An archived favorite stays a favorite and comes back as one when it is restored.
- A user also keeps favorite frequencies: a frequency with a mode and submode, such as 7.100 MHz LSB or 145.000 MHz FM, recalled on the entry screens with one choice. They belong to the User alone, not to a Logbook, so every Logbook and every device shares them: a row of `frequency_favorites` per user, frequency (in Hz), mode and submode, listed by frequency. The frequency is kept in MHz as the server formats it and must be above zero; the mode must be an ADIF mode that is not import-only, and the submode empty or one of its submodes. Saving one already kept returns it, so the same frequency and mode is never kept twice. They have no name and no order of their own. An API token reads and changes the favorites of its User, whatever Logbooks it reaches, so the desktop client shares them with the web client.
- Live entry, voice entry and the desktop client show them in a list under a star next to the mode: the star is filled when the form's frequency and mode are a favorite, the list saves the form's frequency and mode when they are not, and each row sets the frequency, the band it falls in and the mode at once, or removes the favorite, which can be undone while the list is open. Setting one moves the reports that are still at the previous mode's default, as choosing a mode does. On voice entry it also changes the QSO waiting to be logged; the voice syntax does not name favorites. The desktop client only fills its form, never tunes the rig, and treats the mode as if it had been chosen on the screen. There is no keyboard shortcut for them.

### Storage Shape

- Core fields (call, band, mode, date and time, station, QSL state and so on) are columns; the rest is a JSON string map.
- A field that has a column is not duplicated in the JSON. Unknown standard fields and `APP_*` are not dropped.
- Values are kept as their ADIF strings; normalized forms for search (the normalized callsign, time in seconds, frequency in Hz) go to derived columns.
- Because values are kept as they arrived, ADIF enumerations (`BAND`, `MODE`, `QSL_SENT`, `QSL_RCVD` and so on) are compared ignoring ASCII case.
- Composite foreign keys enforce that a QSO belongs to the same Logbook as its Station and its Instrument, and that an export batch contains only QSOs from its own Logbook.
- The tables are described in [schema.md](schema.md).

### FREQ and Parks

- A QSO without FREQ can be saved. The server and imports never fill in a representative frequency.
- In the web client's editors (live entry, voice entry, QSO editing), choosing a band sets the frequency field to that band's representative frequency, overwriting what was there, and typing a frequency moves the band to the one containing it. The representative frequencies are a client table next to the band table, each inside its band (for example 7.000, 14.000, 18.100, 144.000 and 430.000 MHz). A frequency outside every band leaves the band alone. Live entry and voice entry start on a device with the default band's representative frequency; the frequency is empty only when the user cleared it, which is remembered like any other value.
- Several parks are one row in the store, with several references in `MY_POTA_REF`; the POTA submission export projects one record per park with `MY_SIG_INFO` expanded. QSOs are not duplicated.

### Users and Permissions

- Instance roles (held by a User): `admin` / `user`.
- Logbook roles (held by a Membership): `owner` / `operator`.
- A User is a person. Signs in with a passkey. Has a personal callsign.
- A Logbook is the unit of a personal or club station and owns its Station Locations and Instruments.
- A QSO's `OPERATOR` defaults to the callsign of the person who entered it, and `created_by` / `updated_by` record the User.
- `Membership.owner` is an application administration right, separate from ADIF's `OWNER_CALLSIGN`.
- An admin's responsibilities lie outside Logbooks: creating and disabling users, invitation links, passkey re-registration, creating and deleting Logbooks and reassigning their owner, revoking other people's tokens, reference data updates, initial setup, backups, and instance settings.
- An owner manages the Stations and Memberships of its own Logbook and renames it, but cannot create Users. A Logbook's name is only shown, never a key: screens, sync and exports use its ID, so renaming changes nothing else, and screens already open show the new name when they next load the Logbooks.
- Even an admin needs a Membership to read QSOs. A rescue operation is explicit and records its reason and actor.
- An operator can edit and delete QSOs entered by others.
- Unlike Stations, Instruments are managed by every member: an operator creates, edits, archives and restores any Instrument of the Logbook, so a member who brings a rig to a club station registers it. Rewriting the past QSOs of an Instrument stays with owners.
- API tokens belong to a User and are limited to Logbooks by scopes. The plaintext is shown only when issued.
- The first admin is created by the CLI's `setup`, which issues a one-time registration URL. Run again for an existing admin, it issues another link, so an admin who lost every passkey, with no other admin to issue one, gets back in; the passkeys they still have stay. Signed in, the admin creates the first Logbook on the Administration screen (`POST /api/admin/logbooks`, with the callsign of its first owner); a signed-in user without a Logbook is told so, and an admin is pointed at that screen.
- Disabling or demoting the last active admin is refused.
- A Logbook keeps at least one active owner: disabling the only active owner of a Logbook is refused until another owner is set, and so is removing or demoting the last active owner.
- Disabling a user deletes their sessions, API tokens and unused registration tokens. Enabling them again restores none of these. Changing a user's callsign is not in the first version.
- Deleting a Logbook is an admin operation that cascades to everything it owns, its rescue records included. The Administration screen confirms by having the Logbook's name typed; the server snapshots the database to `snapshots` first, and a snapshot that fails deletes nothing.
- An admin sets an owner of a Logbook as a rescue with a reason, on the Logbooks section of the Administration screen. The existing owners stay owners.
- Reference data versions are written by an admin (the Server section of the web client's Administration screen) and read by any signed-in user.

### Sign-in and Credentials

- `public_origin` requires a DNS hostname for WebAuthn. IP addresses are refused during configuration validation; local development uses `http://localhost`.
- Sessions, API tokens and registration tokens are random 256-bit values; only their SHA-256 is stored.
- A session lasts 30 days and is extended on use: at most once a day, its use is recorded and its expiry pushed to 30 days from now, but never past 90 days from its creation; after that the user signs in again. Signing out deletes it. A session records the `User-Agent` it was created with (at most 256 characters), so a user can tell their sessions apart, list them and revoke any of them; an admin can do the same for another user.
- Issuing a token requires a Membership in every Logbook of its scopes. A token is revoked by its user or by an admin; an owner cannot revoke the tokens of the Logbook's members.
- A token's `last_used_at` is written at most once a day, so that reads do not become writes.
- A registration token is valid for 24 hours unless `setup` is given another period. Issuing one for a user invalidates that user's unused ones.
- A registration link is `public_origin/register#<token>`. The token is in the fragment, so it never reaches the server's request logs; the client sends it in the registration request.
- Re-registration only adds a passkey. A lost passkey is removed with a separate deletion. A user cannot delete their own last passkey; an admin can delete another user's last one.
- WebAuthn ceremony state is kept in memory. The store keeps the `Passkey` as JSON and does not depend on webauthn-rs.
- A ceremony is used once and expires after 5 minutes. At most 10 000 are in flight; one started past that evicts the oldest instead of refusing everyone with `429`, so memory stays bounded, but a flood of unauthenticated sign-in starts can evict a sign-in in progress, which then has to start again. Request rate limits, on `/api/auth/` above all, are the reverse proxy's. A restart drops the ceremonies and the browser starts again.
- Passkeys are discoverable credentials: registration requires a resident key and user verification, and sign-in asks for no callsign. The WebAuthn user handle is the user ID; a passkey whose row belongs to another user than its handle, or to a disabled user, does not sign in.
- Reading and verifying a passkey, updating its signature counter and creating a session run in one write transaction, so concurrent sign-ins cannot accept a stale counter.
- Completing a registration link consumes it and stores the passkey in one transaction, then signs the user in. A signed-in user adds further passkeys without a link.
- The session cookie is `__Host-session` with `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/` and a 30-day `Max-Age`, which `GET /api/me` renews.
- A state-changing request (any method but `GET`, `HEAD` and `OPTIONS`) is refused when it carries an `Origin` other than `public_origin`, or a `Sec-Fetch-Site` other than `same-origin` or `none`. A request with neither header is not from a browser and carries no ambient cookie, so API token clients need not send them.
- Every response carries `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, a `Permissions-Policy` denying camera and payment and allowing geolocation to the origin only (the Station editor fills the grid locator from the current location), and the `Content-Security-Policy` `frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'`. Responses under `/api` are `Cache-Control: no-store` unless the handler sets its own. The script, style and connect directives belong to the client, which emits them with hashes through SvelteKit's `kit.csp`; the two policies combine. HSTS is the TLS-terminating proxy's.

### Bulk Changes

- A bulk QSL change takes QSO IDs, each with the revision it is based on, and assignments to the QSL columns only. Values are checked against the ADIF enumerations ignoring case and dates as `YYYYMMDD`, and stored as given. Rows that are missing, deleted or at another revision are skipped and reported; the others are updated. Operators can do it.
- Applying an export batch is a bulk QSL change over the batch rows at their recorded revisions, dated with the UTC day of the application: `qsl_card` sets `QSL_SENT = Y` and `QSLSDATE`, `eqsl` sets `EQSL_QSL_SENT = Y` and `EQSL_QSLSDATE`, and `lotw` sets `LOTW_QSL_SENT = Y` and `LOTW_QSLSDATE`. `QSL_SENT_VIA` is not written. `adif` and `pota` batches are records only and cannot be applied. A batch is applied once, in one transaction.
- Rewriting the past QSOs of a Station is reserved for owners. It covers the Station's QSOs, optionally within a QSO time range, and overwrites `STATION_CALLSIGN` and the keys present in the Station's fields, leaving the other fields alone; rows that already match are not touched. A preview returns the number of rows; applying takes that number and refuses with a conflict if it no longer matches.
- Rewriting the past QSOs of an Instrument works the same way and is reserved for owners too. It covers the Instrument's QSOs, optionally within a QSO time range, and overwrites the fixed fields the Instrument has a value for and the keys present in its fields.

### Search

- The client keeps no copy of the Logbook. The log list sends its query to the server and reads the matches newest first, with keyset paging on `(qso_time, id)`, loading the next page as the end of the list comes into view. It can also sort oldest first, or by `call_base` A to Z or Z to A, paging on `(call_base, qso_time, id)`; within one `call_base` the rows stay newest first in both directions. The order is a separate `sort` parameter, not a term of the query, kept in `?sort=` beside `?q=`, and chosen from the log list's sort menu or the headers of the time and call columns. A row arriving over SSE is placed by the same order. The first page carries the total number of matches. Deleted rows are excluded.
- The query is one text syntax, shared by the web UI, the native API (`q` on the QSO search, open to API tokens from the start) and the filters of export batches. It is a list of terms separated by spaces, all of which must hold; a comma-separated value matches any of its parts, a value containing spaces is quoted, and `-` negates a term. The terms are listed in [query.md](../guide/query.md).
- Values are compared as their ADIF strings, enumerations ignoring ASCII case (see Storage Shape). `freq:` and `pwr:` are the exceptions: both sides are read as decimal numbers to six places, exactly, so `freq:14.074` matches `14.0740`; the server compares `freq:` on the derived `freq_hz`. Wildcard and substring terms scan the Logbook's rows; at the size of one station's log no index or full-text table is needed, and FTS5 is added only when that stops being true.
- An unknown field, a bad date or number or a malformed term is `400`, naming the term and its position so the client can mark it, with a code the client words it from (see Localization). A term is never dropped silently.
- Parsing and matching are one implementation, the query crate (see Structure). The server translates each term into SQL, and a store test runs a set of queries both through SQL and through the crate's matcher over the same rows, so the two cannot drift apart. The client uses the crate to show the terms as chips while typing (an unfinished term such as `call:` is shown as pending and the query is not sent) and to test the rows SSE delivers against the query.
- The search, the targets of a bulk change and export batches take `q` alone. The structured filters of the first version (a QSO time range, the Station, band, mode, the call or `call_base`, `QSL_SENT` and `contest_id`) were removed as a second way of saying what `q` says; the Station and the Instrument are named exactly by ID with `station-id:` and `instrument-id:`, which entry screens use for the latest QSOs of their Station.
- Selecting every match in the log list asks the server for the IDs and revisions of all matches (`GET /targets` with the same filters), and a bulk change takes that list (see Bulk Changes). A bulk change is never applied to a query directly, so what changes is what was selected, at the revisions it was selected at.

### Store and Authorization Boundaries

- There are no Repository traits and no separate service layer. Each operation (creating a QSO, archiving a Station and so on) is one concrete function in `server/src/store/`, called by the native API. Smaller SQL helpers inside the store take a plain connection and are not the entry points. A trait or a service layer is added only when it removes a concrete duplication.
- Every operation that writes runs in a write transaction opened with `BEGIN IMMEDIATE`, so the write lock is taken before the first read and a later write never fails with a busy error that `busy_timeout` cannot wait out. The transaction is a type only the store can create, and every public write function requires it; a caller cannot forget to open one or open a deferred one.
- The unit of atomicity is one operation: numbering, checking and saving one QSO happen in one transaction. Bulk work such as an import calls the same operation in batches, a bounded number per transaction, so write transactions stay short. A rerun of an interrupted import is idempotent through IDs derived from the records (see ADIF Import).
- Authorization is a value. The store checks a principal (a signed-in user, or an API token with its user and Logbook scopes) against the user's state, the token's scopes and the Membership, and only then hands out a Logbook access that carries the Logbook, the user and the role. Logbook operations take the Logbook from that access rather than from a separate argument, so an access for one Logbook cannot be used on another.
- Access values retain their principal and are revalidated at each store operation. Writes revalidate inside their write transaction, including the current user state, token scopes and required role; an old access cannot bypass removal, demotion or revocation. QSO creation uses the user's current callsign for the default `OPERATOR`.
- Operations reserved for owners (Stations, Memberships, rewriting the QSOs of an Instrument) require an owner access, which can only be obtained from a Logbook access whose role is `owner`. Instance operations (users, Logbooks) require an admin access, which only a signed-in admin obtains; API tokens never do.
- An admin outside a Logbook obtains a Logbook access only through a rescue, which records the actor, the action and the reason in `rescue_operations` in the same transaction as the operation.
- A rescue access is valid only while its issuing write transaction is active and its uncommitted audit row is visible on the operation's connection. Commit or rollback invalidates it, and it cannot be used from another connection. Each rescue operation also revalidates the admin's current authority.
- The authorization lives in the store, not in the web layer.
- A Logbook or a row the principal cannot access is reported as not found, the same as one that does not exist.

### ADIF Input and Output

- Lengths are codepoints by default; bytes or UTF-16 units can be chosen as an export option. An export can also be written in Shift_JIS, Windows-1252 or ASCII, and then lengths are that encoding's bytes; a character the encoding cannot represent refuses the export unless it is replaced by `?`, written as `&#NNN;`, or its field is left out. The text is still produced as UTF-8 and encoded last, so the stored values never change.
- An import reads a file that is not UTF-8 as the configured fallback encoding (`[adif] fallback_encoding`, Shift_JIS by default), or as the encoding asked for. Unless a length unit is asked for, each non-ASCII value is read in the unit after which the next tag follows (codepoints, bytes of the file's encoding or UTF-16 units), keeping the unit of the previous value when it fits. Loggers disagree here: CQRLOG mixes bytes and codepoints in one record, Turbo HAMLOG counts Shift_JIS bytes, and Qt and Delphi programs count UTF-16 units. The import reports the encoding and the units it met.
- A field name is what the ADIF specification allows: ASCII letters, digits and underscores, starting with a letter, read ignoring case and stored upper-cased. `EOR` and `EOH` are not field names. A record with another name (a `USERDEF` name with spaces, say) is refused, on entry and in an import.
- A field value is at most 2048 bytes and a QSO has at most 1024 fields outside the columns; the names of passkeys, tokens, Stations and Logbooks are at most 2048 bytes. The bounds are checked where a `Qso` is built and again when it is checked before a write, so nothing larger is stored. A filter lists at most 100 values.
- Reading and writing use adif-manip (github.com/kb10uy/adif-manip), renamed from adif-reader when the writer moved in as its `write` module, after the export output had been checked against real QSL card, contest and POTA submissions. `server/src/domain/adif.rs` maps a `Qso` to and from its fields and writes the header; the expected output stays in `fixtures/adif/` for the client tests to share.
- Apart from the query crate (see Structure), no shared crate is split out; for now everything stays within this repository.
- The QSL state of record is the ADIF fields (`QSL_SENT` / `QSL_RCVD` / `*_VIA` / `QSLSDATE` / `QSLRDATE`, `EQSL_QSL_*`, `LOTW_QSL_*`). No separate set of booleans is kept.
- qsl_required is `QSL_SENT in {R, Q}`; received is `QSL_RCVD in {Y, V}`.
- An export records the target UUIDs and `revision`s as a batch, and after the external processing only the matching rows of that batch are updated.

### ADIF Import

- An import either adds new QSOs or merges QSL confirmations into existing ones. The request names it by the source (`new`, `lotw`, `eqsl` or `card`); it is never guessed from the file.
- Without `--apply` an import only previews: it reads, checks and matches every record and reports what applying would do, writing nothing. The preview runs in one read transaction and takes no write lock, so a large preview never blocks entry; duplicate warnings against the earlier records of the file are computed in memory. With `--apply` it writes, a bounded number of records per write transaction.
- A new QSO's ID is derived from its record: a UUID v7 whose timestamp is the QSO time and whose remaining bits come from the SHA-256 of the Logbook ID, the record's fields as read (names upper-cased and sorted, values as they arrived) and the number of identical records before it in the file. A rerun of an interrupted or repeated import meets the rows it already created and the idempotent create returns them; a deleted row stays deleted. Editing some records and rerunning adds only those records.
- A new-QSO import takes an optional Instrument besides its Station. Its values are baked in after the ID is derived, and only where the record has none, so the record's own `MY_RIG`, `MY_ANTENNA` and `TX_PWR` win and choosing another Instrument for a rerun does not change the IDs.
- The timestamp of such an ID is the QSO time rather than the time of entry. Nothing relies on it: insertion order is `seq`.
- Records that cannot be read or checked are skipped and reported by their position; the others go ahead. A possible duplicate of an existing row is a warning, as on entry.
- A QSL merge writes only the fields of its source, and only towards received:

  | Source | Confirmation in the record | Fields written |
  | --- | --- | --- |
  | `lotw` | `LOTW_QSL_RCVD`, or else `QSL_RCVD` (as in `lotwreport.adi`), is `Y`; the date is `LOTW_QSLRDATE`, or else `QSLRDATE` | `LOTW_QSL_RCVD = Y`, `LOTW_QSLRDATE` |
  | `eqsl` | `EQSL_QSL_RCVD`, or else `QSL_RCVD`, is `Y`; a record with neither is a confirmation (an eQSL inbox); the date is `EQSL_QSLRDATE`, or else `QSLRDATE` | `EQSL_QSL_RCVD = Y`, `EQSL_QSLRDATE` |
  | `card` | `QSL_RCVD` is `Y` or `V`; the date is `QSLRDATE` | `QSL_RCVD` as given, `QSLRDATE`, and `QSL_RCVD_VIA` when the record has it |

- A confirmation without a date is dated with the UTC day of the import. A QSO whose received field for the source is already `Y` or `V` is left alone, and nothing is set back to `N`.
- Other fields a confirmation carries (`DXCC`, `CQZ`, `ITUZ`, `STATE`, `CNTY`, `GRIDSQUARE`, `IOTA` in LoTW's report) are never applied; the preview counts the QSOs where they differ.
- A record matches the live QSOs of the Logbook, or of one Station when it is given, with the same call ignoring case, the same band (from `FREQ` when the record has no `BAND`), a mode where the `MODE` or `SUBMODE` of one equals the `MODE` or `SUBMODE` of the other ignoring case, `TIME_ON` within 15 minutes, and the same `STATION_CALLSIGN` when the record has one.
- Matching searches every candidate page before deciding whether a match is unique. Exactly one match is merged. No match is reported as unmatched. Several matches are ambiguous and never merged unless all of them are already received; they are resolved by hand. Unmatched, ambiguous and invalid records can be written to a rejects file as ADIF. Two records matching the same QSO merge the first only.
- Applying is a bulk QSL change at the revisions read while matching, so a row changed in between is skipped and reported. A rerun finds the merged rows already received and changes nothing.

### Backup and Restore

- `backup` writes a `VACUUM INTO` copy of the database while the server runs, to a timestamped file in the `backups` directory next to the database or to a given path. `--keep N` then removes all but the newest N backups in that directory. Scheduling and off-site copies are left to the host (cron, a systemd timer).
- A backup is the database only. Reference data is installed again by an admin; the configuration belongs to the deployment.
- `serve` holds an exclusive lock on a `.lock` file next to the database. `restore` takes the same lock, so it refuses while the server runs and the server cannot start during a restore.
- `restore` copies the backup next to the database and checks the copy: `PRAGMA integrity_check`, and every migration applied in it known to this binary with the same checksum. It applies pending migrations to the copy and, in one transaction, replaces the cursor generation of every Logbook and deletes every session and every unused registration link. Only after the copy is ready does it snapshot the current database to `snapshots` and replace it with the copy. A preparation or replacement failure leaves the current database in place. The backup file itself is never modified.
- Sessions and registration links are deleted because the backup may hold some that were revoked after it was taken; everyone signs in again. API tokens revoked after the backup come back too, so the restore lists the tokens it restored for an admin to review.
- Restoring from the web UI, scheduled backups inside the server, continuous replication and restoring a single Logbook are not in the first version; a single Logbook travels as an ADIF export.

### Delivery and Sync

- Use SSE. Do not use WebSocket.
- The event `id` is `updated_seq`. Reconnection uses `Last-Event-ID`; after a restart a client that keeps a copy of the Logbook passes its stored cursor as `?after=`. When the browser gives up on a stream (a `401`, `404` or `503`), the web client opens a new one after its last `updated_seq` with `?after=`, waiting 2 seconds and doubling the wait up to a minute until a `hello` arrives.
- Differences are not narrowed by filters; the whole Logbook is streamed and the client re-evaluates its display conditions against the current rows.
- A client that keeps a copy syncs initially by taking the maximum `updated_seq` at start as H, fetching everything, then reading `after H`. Rows that arrive twice are upserts and therefore harmless.
- The web client keeps no copy (see Search) and no cursor across reloads. It opens the stream, which starts at the latest `updated_seq`, then runs its query. The loaded rows, the query, the checked rows and the scroll position are kept in memory for as long as the browser tab lives, so returning to the log list from another screen shows them without a request. Moving between the screens of a Logbook keeps its stream open; leaving the Logbook closes it, and coming back reopens it with the stored cursor as `?after=`, so the changes made meanwhile are replayed into the loaded rows. An event updates a loaded row in place by its ID. A row that stops matching stays where it is, marked, until the query runs again. A new row that matches is inserted in order without moving the scroll position. A new row outside the query is only counted, in a small "N new outside this query" next to the list. A changed cursor generation reruns the query.
- Attach `keep_alive` to axum's `Sse`.
- A stream opens with a `hello` event carrying the cursor generation and the latest `updated_seq`. Successful state-changing requests wake every stream at once, except those under `/api/auth`, which anyone can call and which would otherwise let an anonymous caller make every stream reread. At most 64 streams are open per server; a further one is refused with `503` and the client retries later. The streams also poll every 10 seconds, which ends the stream of a caller who lost the Logbook or whose session expired or was deleted. Session checks do not renew the session. A stream queues at most one page of 500 QSOs and rechecks authorization on writes and polling deadlines even while sending that queue. Streams discard queued events when the server shuts down, so graceful shutdown does not wait on them.
- After restoring a backup, change the cursor generation of every Logbook to demand a full resync. A client whose stored generation differs discards its cursor and syncs from the start.

### Web Client Routes

- Every screen has a path of its own, so moving between screens adds browser history and a screen can be bookmarked or reloaded. The navigation's link to the log list carries the last `?q=` and `?sort=`, so the list comes back as it was left. The client routes as a single-page app; the server already answers any other path outside `/api` with `index.html`.
- Screens of a Logbook carry its ID: `/logbooks/{logbook_id}` (the log, titled `Logbook`), `/entry`, `/voice`, `/qsos/{qso_id}` (editing one QSO), `/stations`, `/stations/{station_id}`, `/instruments`, `/instruments/{instrument_id}`, `/qsl-management`, `/import-export`, `/members`, `/settings` (the Logbook's name and area code field) and, on mobile, `/more`. Switching the Logbook keeps the screen. Screens of the user do not: `/settings/account`, `/settings/tokens`, `/settings/voice` (the speech language of this device) and `/settings/appearance` (the theme, the log table density and the display language of this device, see Localization), with `/settings` listing them on mobile. Settings groups its sections by what they belong to (the user, this device, the Logbook), and shows the current Logbook's settings and members as the Logbook's group, at that Logbook's `/settings` and `/members`. The instance's screens are Administration, reached from the sidebar and from More by admins only: `/admin/logbooks` (every Logbook with its owners, creating one, deleting one and adding an owner as a rescue), `/admin/users` (every user with their role, state and passkey count, and adding one, which issues their registration link at once), `/admin/users/{user_id}` (a user's role, disabling and enabling them, issuing a registration link, and their passkeys, sessions and API tokens to remove or revoke) and `/admin/server` (the server's version and commit, and the reference data versions with their installation), with `/admin` listing them on mobile; a user who is not an admin is sent to Settings. `/` opens the log of the Logbook last used on the device; sign-in is `/login` and registration `/register` (see Sign-in and Credentials). The document title is the name of the screen alone, as in `Live Entry` or `QSL Management`; a Station, an Instrument and a settings or administration section add the screen after their own name (`Home - Stations`, `IC-705 - Instruments`, `Account - Settings`, `Server - Administration`), and a user adds the section after theirs (`JA1ABC - Users - Administration`). A screen without a name of its own is `JL1HIS Logger`.
- The log keeps its query in the URL as `?q=`, in the text syntax of Search, so a query can be bookmarked and reopened later. A sort order other than newest first is `?sort=`. The QSO open in the detail overlay is `?qso={qso_id}`. Typing a query, changing the sort order, opening or closing the overlay replace the current history entry rather than adding one. Checked rows stay out of the URL.
- The columns of the log table on wide screens are a per-device setting shared by every Logbook: the ordered list of shown columns, left to right, kept in local storage. The built-in columns are Date / UTC (one column), Call, QSL S / R, Band, Freq, Mode, RST S / R, Station and Park, shown by default, and LoTW S / R, eQSL S / R, TX Power, Contest (`CONTEST_ID`) and Number S / R (`STX_STRING` / `SRX_STRING`), hidden by default; any ADIF QSO field or `APP_` field can be added as a column of its own, named `adif.{FIELD}` as in Search. The check box column stays first. The narrow-screen list keeps its fixed layout.
- On wide screens the sidebar can be collapsed to a narrow bar of icons, a per-device setting kept in local storage. Collapsed, it shows the Logbook switcher as an icon, the sync state as a dot whose text is its tooltip and the user's callsign turned on its side, reading top to bottom; it never collapses on its own. Mobile keeps its tab bar.
- The theme is light, dark or the system's (the default), a per-device setting kept in local storage and chosen at `/settings/appearance`. Every color token in `client/src/theme.css` is a `light-dark()` pair, so the choice only sets `color-scheme` through `data-theme` on the document, which `client/static/theme.js`, loaded by `app.html` before the app (the CSP allows no inline script), restores before the first paint. The log table density is another per-device choice there, Normal or Compact (Normal by default); Compact sets `data-compact` on the document, which the `compact:` variant of `client/src/app.css` turns into tighter cell padding in the desktop log table, the Latest at this Station table of live and voice entry and the Before with list of live entry; `theme.js` restores it the same way, and the root layout applies it again when the app starts, since a service worker that has not yet been replaced still serves the `theme.js` of the build it cached.
- Every per-device setting of the web client (the theme, the density, the collapsed sidebar, the log columns, the speech language, the last Logbook and each Logbook's entry form) is declared once in `client/src/lib/device.ts`, with its local storage key, how it is read, the defaults filled in for what an older version did not store, and how it is written; nothing else touches local storage, except Paraglide for the display language. A flag is stored as `1` and removed when off. `theme.js` cannot import it, so a test keeps the keys it reads equal to the module's. The desktop client keeps its own settings under its own keys through the same helpers.

### Localization

- The web client's text is localized. The locales are English, the source every message is written in first, and Japanese. Messages are Paraglide JS (inlang) message files, one per area of the client and locale (`client/messages/en/log.json`, `client/messages/ja/log.json` and so on, listed in `client/project.inlang/settings.json`), compiled into typed functions in `client/src/lib/paraglide/`, so a missing or misspelled key fails `svelte-check`. Message keys start with their area (`log_`, `entry_`) except the shared ones in `common.json`. A test keeps the Japanese keys equal to the English ones; at run time a missing message would fall back to English.
- The inlang plugin that reads the message files is the `@inlang/plugin-message-format` package, loaded from `node_modules` by path, so compiling the messages never fetches code from the network.
- The locale is a per-device setting kept in local storage, chosen at `/settings/appearance`. Without a stored choice it is the first of the browser's languages that is a locale, or else English. The locale is never part of the URL, so every path stays as in Web Client Routes. The document's `lang` follows it, and changing it reloads the page.
- The display language and the speech language of voice entry are separate settings; changing one never changes the other.
- Translated: labels, buttons, headings, notices, warnings, errors, document titles (the English titles in Web Client Routes are the source) and the display names of fields and search chips (`My park`, `QSL sent`). Numbers are formatted with `Intl` for the locale, and plurals belong to the messages.
- Not translated: ADIF field names and values, enumerations (bands, modes, QSL values such as `R` or `Y`), callsigns, the keywords of the query syntax (`call:`, `no:`) and the words of the voice syntax, which follow the speech language. QSO dates and times stay ISO dates and UTC `hh:mm` in every locale. The server, the CLI, logs and ADIF output stay English.
- The server keeps the English `error` text of its errors, for API clients and logs. An error the web client words for the user carries a stable snake_case `code` and its parameters as fields beside it, as a query error already does (`code`, `term`, `index`, `start`, `end`), and the query crate's `ErrorKind` codes serve the server's `400` and the client's WASM chips alike. The client words an error from its code, and shows the `error` text as it is for a code it does not know. Codes are part of the API: renaming one is a breaking change.
- Codes are given to errors a user can reach through the web client: a QSO that does not check (`qso_missing`, `qso_invalid`, `field_repeated` and the other `qso_*` codes), a Station's, Instrument's or area code field's fields, names, Memberships and tokens, passkeys and registration links, import and export batches, conflicting updates, query terms and things not found (`not_found` with the thing in `what`). In the store, `StoreError::Invalid` and `StoreError::Conflict` carry a `Fault` whose code and parameters the web layer adds to the body; a fault without a code keeps only its text. Errors only an API client can cause, such as a malformed `If-Match` or `Last-Event-ID`, and errors of instance administration have no code. Warnings are already a `kind` with parameters and are worded by the client.

### Offline Entry

- The client keeps no copy of the Logbook, so offline there is no log list, no lookup and no duplicate warning.
- Entry keeps only its own QSOs. Live entry and voice entry write each QSO to their shared queue in IndexedDB and send it at once. That first send waits at most 5 seconds, during which the QSO is not shown as queued and logging the next one is disabled; a send still unanswered then counts as the server being unreachable. A QSO that could not be sent stays in the queue with the reason. The screen shows the queued QSOs of the chosen Station, and the user sends those explicitly or discards one; nothing retries in the background. Resending is safe because `POST` is idempotent on the UUID, and duplicate warnings come back in the `warnings` of the send.
- The service worker caches the app shell, so the PWA starts offline; it never caches `/api`.

### Live and Voice Entry

- Voice entry is one screen of the PWA and shares the offline queue with Live entry.
- Voice entry shares Live entry's per-device settings (Station, Instrument, frequency, band, mode and contest, the serial included), so switching between the two screens carries them over. The spoken QSL requests map as follows: "requested" sets `QSL_SENT = R`, "one way" sets `QSL_SENT = N` and `QSL_RCVD = R`, and the area code is spoken as "area" (Japanese "エリア") followed by spelled letters and digits, up to 16 characters, which go to the Logbook's area code field, or nowhere, with a note on the screen, when the Logbook has none. There are no JCC / JCG words in the voice syntax.
- Live entry takes the Logbook's area code field, when it has one, and the same QSL request as voice entry (none, requested, one way) on one row under the name and QTH. It has a collapsed extra fields panel: `TX_PWR` (watts, under the Instrument's rule), `NOTES`, and any other ADIF 3.1.8 QSO field that is not import-only, or an `APP_` field, typed by name. A field the form already has, `STATION_CALLSIGN`, an unknown name or a name given twice blocks logging. The other fields of a Station or an Instrument are checked against the same list of names. A value given there overrides the baked values of the Instrument and the Station, such as the Instrument's `TX_PWR`. TX power stays for the next QSO while the screen is open, and is cleared when the Instrument changes; while it is empty, the field shows the Instrument's `TX_PWR` as its placeholder. Notes and the other fields are cleared with the QSO, both when it is logged and by Clear (Esc), and the reports go back to the mode's default. The form is cleared as soon as the QSO is in the queue, so the next call can be typed while it is sent.
- The QSO editing screen edits the fields the entry screens write: call, date and time, frequency, band, mode and submode, the reports, name, QTH, the Logbook's area code field, comment, notes, `TX_PWR`, and the paper QSL state (`QSL_SENT`, `QSL_RCVD`, both `_VIA` and both dates). Every other field of the QSO is listed by name under "Other ADIF fields", where it can be changed, removed, or added with the same rules as the extra fields of Live entry, except that `STATION_CALLSIGN`, `OPERATOR` and the `MY_*` fields are shown read-only as the Station at the time. LoTW and eQSL states are shown, not edited. The band, frequency, sideband and default reports follow each other as in Live entry: a changed band or frequency moves `LSB` / `USB` with it, and a changed mode replaces a report still at the previous mode's default.
- Live entry and voice entry choose the Instrument with a select next to the Station's, and the QSO editing screen chooses it as well. None is a valid choice. The voice syntax does not change it. A remembered Instrument that is archived or gone is cleared. The queue holds the Instrument's ID, and the server bakes its values in when the QSO is sent, as it does for the Station. When the user has favorites, the Station and Instrument selects show them first in a group of their own, and a Station not yet chosen on the device defaults to the first favorite. Every row of the Station and Instrument lists has a star at its left that marks and unmarks the favorite.
- Speech recognition is Vosk in the browser. The models are not in the repository: `client/scripts/setup-vosk.sh` (also `pnpm run models`) or `client/scripts/setup-vosk.ps1` downloads them into `client/static/models`, and puts each model's vocabulary into `client/.vosk` for the vocabulary tests, which read it when `VOSK_WORDS_EN` or `VOSK_WORDS_JA` is not set. The server serves them with the app, and the browser keeps a loaded model in IndexedDB so voice entry works offline. The service worker does not precache them. The Vosk worker is copied out of `vosk-browser` into `static/vosk-worker.js` at build time and started as a same-origin worker, so the page's CSP needs neither `blob:` workers nor `unsafe-eval`.

### Reference Data

- Updates are installed by an admin from a file they have downloaded, by uploading the archive on the Server section of the web client's Administration screen (`PUT /api/reference/cty`). The server fetches nothing over the network.
- The upload installs through one function in `store`: it parses and checks the whole file in memory, puts it where the configuration points (through a staging file with a unique name in the same directory and a rename), and records the version with the file's SHA-256 in `reference_versions`. Validation and database update errors preserve the previously installed file and version, and the staging file is removed; if committing fails after replacement, the previous file is restored (or the new file removed on a first installation). The replacement, the commit and any restoration run as a task of their own, so a request that is cancelled midway (the client disconnects) cannot leave a file the recorded checksum does not match. The stored path comes only from the configuration, never from the upload or the archive. The version of `cty` comes from the `=VER` entry of its `cty.dat`, or else the UTC date of the installation.
- The one kind is `cty`, a CTY zip archive from country-files.com, either Big CTY (`bigcty-YYYYMMDD.zip`) or the contest files (`cty-NNNN.zip`), stored as it is; the server reads `cty.dat` and `cty.csv` out of it in memory when it loads the data set. Lookups use `cty.dat` (through `callfind`); `cty.csv` gives only the ADIF DXCC entity code of each primary prefix, because its alias lists do not match `cty.dat`. The archive is refused unless both files are at its root, `cty.dat` parses, and the primary prefixes of `cty.csv` match the entities of `cty.dat` one to one (WAE-only entities, `*IT9`, included; their codes are not used, since lookups fold them into their DXCC entity).
- An archive is untrusted input, so reading it is bounded: at most 4 MiB uploaded (a route body limit) and 256 entries, no two entries with the same name, local headers consistent with the central directory, only the entries named exactly `cty.dat` and `cty.csv` read, each through a 4 MiB limit on the decompressed bytes regardless of the sizes the headers declare, no encrypted entries, only Stored and Deflate, and only UTF-8 text. Nothing is extracted to disk. A refused upload is a `400` with code `reference_invalid` and the reason, never a server path; file system errors are logged and answered as a generic `500`.
- Before the archive format, `cty` was a plain `cty.dat` and a separate `dxcc` kind held the codes as a TOML table. Migration 9 forgets both rows, so an upgraded instance has no `cty` until an admin installs an archive (lookups answer without the entity meanwhile), and the `dxcc` setting of `[reference]` is no longer accepted.
- The server reads a data set when it is first needed and keeps it until the version or checksum recorded for its kind changes, so an installation takes effect without a restart. A file that no longer matches its recorded checksum is an error rather than being served. A kind that was never installed is simply absent: lookup answers without the entity.
- DXCC and zones already recorded on existing QSOs are not changed automatically by a reference data update.
- The tables the ADIF specification defines are built in rather than reference data: they change with a new ADIF version, about once a year, which comes with code changes anyway. They are generated at build time from the specification's CSV exports, committed byte for byte under `assets/adif/` (see its README for the files, the source and the upgrade steps); they follow ADIF 3.1.8. `server/build.rs` writes `const` tables into `OUT_DIR`, included by `domain` (bands, modes, QSL values, DXCC entities with their deleted flags, subdivisions), and `pnpm run adif` writes `client/src/lib/adif/tables.ts` (bands, modes, QSL values, QSO field names, DXCC entities with their deleted flags, which the Station editor searches by code or name) before the client's `dev`, `build`, `check` and `test`; neither output is committed. A malformed file, a row of another ADIF version, a band overlapping the one before it, a submode of two modes or an import-only mode that is no submode fails the build, naming the file and row. Exports write the version of the tables as `ADIF_VER`, and `GET /api/version` reports it as `adif`, shown in the client's server settings.
- The client's choice lists stay hand-written where they are curated rather than complete: the band groups with their representative frequencies and labels, the mode choices, and the localized QSL labels. Tests keep them inside the generated tables, the bands and QSL labels covering them exactly, so a new band or QSL value fails a test until it has a label.
- The native API serves the subdivisions of one DXCC entity from the built-in table, so that the client offers `STATE` and `MY_STATE` as a choice (prefectures for 339): `GET /api/reference/subdivisions/{dxcc}` answers `[{code, name}]` ordered by code, to any signed-in user as the versions are. The choices leave out the subdivisions the specification marks deleted or import-only. An entity without subdivisions is an empty list and a code that is not an ADIF DXCC entity code is `404`; in both cases the client falls back to free text. The client fetches a list when a form needs it and keeps it until the page is reloaded; the table changes only with the server. No other data set is served: `cty` is not, for offline lookup or otherwise.
- Subdivisions were a reference data kind installed from a TOML file before they were built in. Migration 10 forgets its row, and the `subdivisions` setting of `[reference]` is no longer accepted.
- POTA park names were a `parks` kind (a TOML table of `name_en` and `name_ja`) that nothing displayed. It is removed until a screen needs park names; migration 11 forgets its row, and the `parks` setting of `[reference]` is no longer accepted. Park references in `MY_POTA_REF` are unaffected.
- Modes and submodes are the ADIF Mode and Submode enumerations in full, with the import-only modes marked. Where the Mode and Submode tables disagree, the table takes the union, in the order of the Mode table's list followed by the submodes only the Submode table names; an entry of that list that is not a submode but whose space-separated words all are (`MFSK128 MFSK128L` in 3.1.8, a missing comma) counts as those words. An import-only mode stands for the mode it is a submode of. A QSO whose `MODE` is unknown, whose `SUBMODE` is unknown, or whose `SUBMODE` belongs to another mode is not refused; creation reports it in `warnings` and an import preview reports it per record. The names spoken in voice entry (`USB`, `FT4` and so on) belong to the client.
- JCX is handled as a string, keeping leading zeros.

### Migrations and Deployment

- The server reports its package version and the Git commit it was built from (`GET /api/version`), shown in the client's server settings. `build.rs` takes the commit from `GIT_COMMIT` when it is set and from `git rev-parse HEAD` otherwise; the Docker build has no `.git`, so the Image workflow passes the commit as the `GIT_COMMIT` build argument. A build that knows neither reports no commit.
- Migrations are embedded in the binary with `sqlx::migrate!()` and applied forward-only. `serve` applies the pending ones at startup; a `migrate` subcommand applies them explicitly, and a configuration setting turns the automatic run off for a deployment that wants the explicit step.
- sqlx records each applied migration with its checksum in `_sqlx_migrations`, so an edited applied file stops the server at startup instead of running.
- Before applying pending migrations, the server snapshots the database with `VACUUM INTO` under the data directory. There is no downgrade; rolling back means restoring that snapshot.
- One process owns the database file, so there is no separate migration job or init container. A deployment is one container holding the binary and `client/build`, with the data directory (configuration, database, reference data, snapshots) on a volume and TLS terminated outside.
- Every setting is in one TOML configuration, `config.toml` in the working directory unless `-c` names another; nothing is read from the environment but `RUST_LOG`, and there is no `.env`. Relative paths in it are relative to its own directory, so the data directory holds the configuration with what it points to. `serve --listen` and `--web-dir` override the file, so that a container image carries its own listen address and web app.
- The server accepts connections itself with hyper's automatic HTTP/1 and HTTP/2 handling: request headers must arrive within 30 seconds, a request body may pause for at most 30 seconds between chunks, and HTTP/2 connections are pinged every 30 seconds and dropped after 10 seconds without an answer. Shutdown stops accepting, ends the event streams and gives open connections 10 seconds. The reverse proxy adds its own limits, HSTS and request rate limits.
- Query macros that need the schema at compile time keep their `cargo sqlx prepare` output in the repository, refreshed whenever a migration is added.

### Lookup

- The native lookup, `GET /api/logbooks/{id}/lookup?call=`, returns the `cty.dat` entity (name, ADIF DXCC code when `dxcc` is installed, continent, CQ and ITU zones, position) and the previous contacts in that Logbook matched by `call_base`: the latest non-empty `NAME`, `GRIDSQUARE`, `QTH`, `STATE`, `CNTY`, `IOTA` and `QSL_VIA` under their ADIF names, the number of QSOs and the latest of them. It can be narrowed to Stations. Given the band, mode, date and time of the QSO being entered, it also returns its possible duplicates, so the entry screens make one request for a callsign rather than one for the lookup, one for the duplicates and one for the latest QSO; they send it once typing has paused for 500 ms.
- The work lives in `domain` and `store`.
- The client asks the server. It keeps no copy of the Logbook, so it has no previous contacts to show while offline (see Offline Entry).

### Desktop Client

- The desktop client is for entry: a small window that sits beside the operator's other radio programs. It opens at 800 by 600, where the form, the lookup and several of the latest QSOs fit, and shrinks to 640 by 480, where the whole form still fits: below 760 pixels wide the UTC date moves above the time, and the latest QSOs give up their room first.
- It behaves like a desktop program rather than a page: only the latest QSOs, error messages and the server's URL can be selected, and the WebView's context menu is replaced by a native one, shown only on text: Cut, Copy, Paste and Select all on text fields, and Copy on selected text.
- It signs in with the server's URL and an API token the user creates in the web client, not with a passkey, which is bound to `public_origin`.
- The URL is reduced to its origin, so a pasted address of any web client page works. It must be `https`, except on the loopback address or `localhost`, because the token travels with every request.
- Signing in checks the token with `GET /api/logbooks` from the Rust side, which sends no `Origin` and so passes the server's origin check. A `401` refuses the token; a token that reaches no Logbook is refused as well. `GET /api/me` also takes a native token, so the window title shows whose token it holds (`JL1HIS — JL1HIS Logger`); without an answer it is the app's name alone.
- The token is kept in the operating system's credential store (Windows Credential Manager, the macOS Keychain, the Secret Service), keyed by the URL, never in a file. Signing out deletes it and keeps the URL to fill the sign-in form.
- The settings are one TOML file, `config.toml` in the app's configuration directory (`%APPDATA%\org.kb10uy.jl1his-logger\` on Windows), read and written by the Rust side so it can also be edited by hand: the server's URL, the language, the theme and the `[rig]` table. `--config <path>` names another file. A debug build uses `config.dev.toml` and the credential service `org.kb10uy.jl1his-logger.dev`, so running `pnpm tauri dev` never touches an installed app's settings or token.
- At start the client checks the saved token. A refused token returns to the sign-in form with the URL filled in; an unreachable server keeps it signed in, since entry must work offline.
- The desktop client's text is localized like the web client's, with its own messages under `desktop/messages/`. The language is System (the operating system's), English or 日本語, chosen on the settings screen and kept as `language` in the settings file, which the WebView mirrors at start and reloads once when the two differ. The web client's code it imports speaks the same language. It imports the web client's `client/src/theme.css`, so both share the tokens, fonts and base styles. The theme is System, Light or Dark, kept as `theme` in the settings file; it sets the window's theme, so the title bar follows, and the WebView mirrors it at start like the language.
- What it reads from the rig through rigctld (frequency, mode) fills its own form only. Nothing about the rig is sent to the server, which has no rig state.
- The settings screen, opened from the gear in the status bar, holds the rig, the server (with Sign out) and the appearance (the theme and the language). Changes are saved as they are made.
- The Rust side reads rigctld over TCP with its extended protocol (`\get_freq`, `\get_mode`, the model from `\dump_caps`) at the chosen interval (0.5 to 5 seconds), reconnects every 5 seconds while it cannot, and passes each change to the WebView. It is off until turned on in the settings. Each poll asks `\get_vfo` first: hamlib resolves the current VFO to the last one it saw rather than asking the rig, so a VFO chosen on the front panel would otherwise go unnoticed and the other VFO's frequency and mode would be read for as long as the connection lasts. A rig that cannot report its VFO is not asked again on that connection.
- The rig's frequency fills the form when the rig moves; typing another frequency holds until it moves again. The rig's mode and the logged mode are separate, since the rig reports PKTUSB for FT8, FM for C4FM and so on. When the rig changes mode, a logged mode that fits it is kept (the SSB sideband follows the rig); otherwise the logged mode becomes the one chosen for that rig mode, `[rig.modes]` in the settings, or a default (FT8 for PKTUSB and PKTLSB). Choosing a fitting mode on the entry screen updates that choice; choosing one that does not fit is logged as chosen and marked as a mismatch. A tag beside the mode shows the rig's mode and whether the logged mode was kept, followed or does not fit.
- The entry screen is the web client's live entry laid out for the small window: Station and Instrument above the form, the contest settings in a bar under them when contest mode is on, the form, the latest QSOs at the Station, and a status bar with the server and the queue. The Station choice spans every Logbook the token reaches, grouped by Logbook, and choosing a Station chooses its Logbook; the Instruments are that Logbook's. The lookup line under the call also shows the last QSO with it, since the window has no room for the list of earlier QSOs.
- It reuses the web client's pure logic (the QSO record, bands, modes, contest exchanges, the queue) by importing `client/src/lib` as `#client/...` through a `link:` dependency on `client/`, not through a shared package.
- Every API request goes through one Rust command that sends it with the token to a path under `/api/` and returns the JSON, so the WebView never holds the token. A `401` returns to the sign-in form as a refused token.
- The queue is the web client's IndexedDB queue inside the WebView and behaves the same: a QSO is written to it before it is sent and stays there, shown on the screen, until the user sends it. The last Station, Instrument, band, mode and contest settings, and a copy of each Logbook's Stations and Instruments, are kept in the WebView's storage, so the screen opens without the server.
- It follows the event stream of every Logbook the token reaches from the Rust side, which reads the Server-Sent Events, reconnects after `after` with a growing delay (2 to 60 seconds) and passes each `hello` and `qso` to the WebView as Tauri events. A QSO of the chosen Logbook updates the latest QSOs at the Station in place, a changed `cursor_generation` reads them again, and a stream that is down shows the server as unreachable. A `401` or `404` stops that stream.
- It takes QSOs and entry fields from other programs on the local machine over UDP (described for those programs in [protocol.md](../guide/protocol.md)), on the addresses listed as `[[listeners]]` in the settings: by default `127.0.0.1:2237`, where WSJT-X sends, and `127.0.0.1:2333`, where other loggers take ADIF, both off until turned on. UDP is enough for the size: a datagram holds up to 64 KiB, and the receive buffer takes the largest. Each datagram is told apart by how it starts: WSJT-X's network protocol by its magic number `0xadbccbda`, this client's own JSON by `{`, anything else as ADIF text. One port can therefore take all three. A listener whose address cannot be bound is shown as failed and retried every 5 seconds.
- A listener does not authenticate its senders, as WSJT-X's protocol does not either: whatever reaches its address logs QSOs with the user's token and Station and drives the entry form. On the loopback address this trusts the programs of the local machine, which gains them nothing, since a program running as the same user can read the token itself. An address that other machines reach, such as `0.0.0.0` for WSJT-X on another computer, trusts them too; the settings screen warns about each such listener but does not refuse it. The Rust side holds at most 1000 received QSOs that the WebView has not taken yet and drops what arrives past that, so a flood cannot grow it without bound.
- Of WSJT-X's protocol, which JTDX and MSHV speak too, only `Logged ADIF` (12) is read. `QSO Logged` (5), sent for the same QSO, and every other message are ignored, and nothing is sent back to WSJT-X. ADIF text may hold several records, with or without a header.
- A complete QSO, from WSJT-X or as ADIF, is logged at once without going through the form: it is written to the queue for the Station and Instrument chosen on the entry screen and sent like one typed in. Its own values win over the Station's and the Instrument's, which fill only what it lacks, as the server always does; a `STATION_CALLSIGN` or `MY_*` value that differs from the Station's is logged as it came and shown as a warning (a shorter grid square that begins the Station's is not a difference). The same QSO (call, date, time on, band, mode) arriving again within two minutes, as when WSJT-X sends it to two ports, is dropped. The Rust side holds what it received until the WebView has written it to the queue, so a reload or the settings screen loses nothing, and a QSO that arrives while no Station can be chosen waits for one. Once such a QSO is on the server, an operating system notification names its call, the program, the band and the mode, with a line for each value that differs from the Station's. Nothing else is notified: a QSO that could not be sent stays in the queue on the screen as any other.
- The desktop client is handed out as the executable alone, without an installer, and on Linux as a Debian package that declares the AppIndicator library the tray loads at run time. Upgrading is replacing that file, or installing the new package over the old one: the settings, the token and the WebView's data with the queue are found by the app's identifier, not by the file's path, so a new version picks them up. The copy still running has to be quit from the tray first, since starting the new one only shows the running one (see below). Nothing updates itself. A toast on Windows takes its name and icon from an app ID that an installer would register with a Start menu shortcut; one registered under `HKCU\Software\Classes\AppUserModelId` alone showed the bare ID and no icon. So on Windows a notification is a balloon of the client's tray icon (`Shell_NotifyIconW` with `NIF_INFO`), which Windows turns into a toast under the executable's own name and icon, respecting quiet time and shown as a banner only, not kept in the notification centre, and nothing is written to the registry or the Start menu. The tray icon's window and ID are not exposed by `tray-icon`: the client finds its own window of the class `tray_icon_app` and uses the ID 2, since `tray-icon` numbers icons from a counter that the builder's own unique ID takes 1 of first, so an update of `tray-icon` has to be checked for a balloon still showing. Should the balloon fail, the toast goes out under PowerShell's app ID instead, which Windows always shows. Elsewhere the notification plugin of Tauri shows notifications.
- This client's own JSON fills the entry form, field by field: `{"v": 1, "type": "set", "fields": {...}}` with ADIF field names (`CALL`, `RST_SENT`, `RST_RCVD`, `SRX_STRING` for the received exchange, `NAME`, `QTH`, the Logbook's area field, `COMMENT`, `FREQ`, `BAND`, `MODE`, `SUBMODE`, `TX_PWR`, `NOTES`, and any other QSO field the form takes as an extra field, ignoring the rest; an empty value clears one), `{"v": 1, "type": "clear"}`, which clears the form as Esc does, and `{"v": 1, "type": "log"}`, which logs it as the Log button does. Only the entry screen takes them. While it is not shown, the Rust side holds the last value of each field a `set` gave (up to 64 fields) and the entry screen fills them in once when it comes back: a program that keeps no form of its own, and only passes on what it picked up, such as a callsign decoded from the air, has nowhere else to keep it. A `clear` drops what is held, since it was meant to empty the form; a `log` is lost, so a QSO is never logged from a form nobody saw. A message of another version, or of a type it does not know, is ignored, so programs and clients of different ages work together.
- A program can subscribe to the entry form, so it can use the client's form as the only one and hide its own: `{"v": 1, "type": "subscribe"}` registers the sender and is answered with `{"v": 1, "type": "form", "fields": {...}}`, which goes to every subscriber too when the form settles on new values (a field left, a message from a program filled in, Esc, a QSO logged, a change of the exchange to send), not on every key. `CALL`, `RST_SENT`, `RST_RCVD`, `SRX_STRING`, `STX_STRING` (the exchanges without the RST), `NAME` and `QTH` are all sent every time, empty ones as `""`: UDP may lose a datagram, and a whole form is put right by the next one where a difference would leave the copy wrong until that field changed again. A form equal to the last one sent is not sent again. The tuning fields are left out, since the client and such a program each read the rig. A subscriber sends `subscribe` every 5 seconds and is dropped after 15 without one, so the answer is the only liveness check either side needs and a program that dies without `unsubscribe` costs nothing; at most 32 are held. `{"v": 1, "type": "bye"}` goes to every subscriber when the client quits, its listeners are changed or it signs out.
- Only a sender on the loopback address can subscribe, on any listener address, and only on a listener whose `subscribe` is on, which it is not by default. Everything else the listeners take is one way, so a forged source address gains nothing; an answer is not, and a small `subscribe` with another machine's address could make the client send it forms. The form may also hold another station's name and QTH, which should not leave the machine because a listener was opened to the network for WSJT-X. The Rust side keeps the latest form, which the WebView passes to it with a command whenever it settles, because a subscription is answered from the listener's thread at once, without asking the WebView. Until the entry screen has passed a form, and after signing out, there is none and a subscription is not answered, which the program reads as the client having no form to share.
- It stays in the system tray. A click on its icon shows the window, and the icon's menu has Show and Quit in the client's language. Closing the window hides it there by default, so it goes on logging from other programs, following the event stream and reading the rig while out of sight; with `close_to_tray = false`, also a switch on the settings screen, closing quits. Quit in the menu always quits.
- Only one copy runs, since a second would find the listeners' ports taken: starting it again shows the window of the one already running, from the tray as well. A debug build is left out, because it shares the app's identifier, which names the lock, and `pnpm tauri dev` should run beside an installed app.

## Remaining Work

- The desktop client does not join multicast groups, so WSJT-X shared with JTAlert or GridTracker through one has to send to it directly; and it does not read N1MM Logger+ broadcasts or WSJT-X's `Status`.
