# Wavelog API v2 Compatibility Layer

Clients written for Wavelog API v2 can talk to jl1his-logger through this
layer. Their base URL becomes `public_origin/wl2`, so their requests arrive at
`/wl2/index.php/api/v2/<resource>`; lookup is also at `/wl2/api/v2/lookup`.
Only a subset of the API is matched; see
"Wavelog API v2 Compatibility Layer" in [decisions.md](../development/decisions.md).

## Requests and Errors

A request carries a `wl2` API token as `Authorization: Bearer <token>`. The
token is fixed to one Logbook, which every request reads and writes. A missing
or unknown token, a native token, a session cookie, or a token whose user lost
the Logbook's Membership is `401`.

Errors are Wavelog's envelope, `{"error": {"code": "...", "message": "..."}}`,
with `details` where Wavelog gives them:

| Status | `code` | When |
| --- | --- | --- |
| `400` | `validation_error` | An unsupported or malformed parameter or body, or a duplicate `POST qso` |
| `401` | `invalid_token` | See above |
| `403` | `forbidden` | A Station ID that is not a Station of the Logbook |
| `404` | `not_found` | An unknown path, or subdivisions of a code that is not an ADIF DXCC entity |
| `409` | `conflict` | A derived QSO ID taken by another Logbook |
| `500` | `internal_error` | A server failure, or a reference file that does not match its installed version |

Successful answers are `{"data": ..., "meta": {...}}`. A Station is addressed
by its Wavelog ID (`station_profile_id`, `station_id`, `station_ids`), and a
Station without one cannot be reached through `/wl2`.

## Stations

`GET station` lists the Logbook's Stations that have a Wavelog ID and are not
archived, ordered by that ID.

| Key | Source |
| --- | --- |
| `id` | `wavelog_id` |
| `uuid` | The Station's ID |
| `name`, `callsign` | The Station's name and callsign |
| `gridsquare`, `city`, `country`, `state`, `cnty` | `MY_GRIDSQUARE`, `MY_CITY`, `MY_COUNTRY`, `MY_STATE`, `MY_CNTY` |
| `iota`, `sota`, `wwff`, `pota`, `sig`, `sig_info` | `MY_IOTA`, `MY_SOTA_REF`, `MY_WWFF_REF`, `MY_POTA_REF`, `MY_SIG`, `MY_SIG_INFO` |
| `dxcc`, `cq`, `itu` | `MY_DXCC`, `MY_CQ_ZONE`, `MY_ITU_ZONE` as numbers |
| `power` | Always `null`; TX power belongs to Instruments, which `/wl2` does not know |
| `active` | Always `false`; there is no active Station here |

A field the Station does not have is `null`.

## Reading QSOs

`GET qso?format=adif` reads the Logbook's live QSOs in insertion order (`seq`),
as ADIF with codepoint lengths. `format` is required and only `adif` is
supported.

| Parameter | Meaning |
| --- | --- |
| `since_id` | Only QSOs whose `seq` is greater; default `0` |
| `page`, `per_page` | Pages of that order, from 1; `per_page` defaults to 1000 and is capped at 5000 |
| `station_id` | Comma-separated Wavelog IDs of Stations, archived ones included |
| `callsign` | The call, ignoring case |
| `callsign_match` | `exact` (the default) or `plain`, which matches the base call, so `JA1ABC` finds `JA1ABC/P` and `KH6/JA1ABC` |
| `band` | Ignoring case |
| `mode` | `MODE` or `SUBMODE`, ignoring case, so `USB` finds `SSB`/`USB` |
| `qsl_filter` | Comma-separated `qsl`, `lotw`, `eqsl`: QSOs confirmed by any of them (`QSL_RCVD`, `LOTW_QSL_RCVD` or `EQSL_QSL_RCVD` is `Y` or `V`). `qrz` and `clublog` are not recorded here and are refused |
| `qso_since`, `qso_until` | `YYYY-MM-DD`, both days included |

```json
{
  "data": { "exported": 2, "lastfetchedid": 1290, "adif": "Generated by jl1his-logger\n..." },
  "meta": { "page": 1, "per_page": 5000, "count": 2, "total": 2, "total_pages": 1, "has_more": false }
}
```

`lastfetchedid` is the `seq` of the last QSO on the page, or `since_id` when
the page is empty, in which case `adif` is `null`; a client continues with it
as the next `since_id`. `total` and `total_pages` count every QSO the
parameters match, `since_id` included, and `has_more` says whether a later
page follows. Edits and deletions are not
reported: `since_id` only ever adds QSOs. The native API's changes and event
stream cover them.

## Logging a QSO

`POST qso` takes one QSO as a JSON object: `station_profile_id` and ADIF fields
named in any case. Values are strings or numbers. `qso_date` may be
`YYYY-MM-DD` or `YYYYMMDD`, and `freq` and `freq_rx` are in hertz, as Wavelog
takes them; they are stored as ADIF (`20261020`, `7.0415`). The Station's
callsign and defaults are baked in as on the native API, and `OPERATOR`
defaults to the token user's callsign. A QSO logged here has no Instrument, so
only the `MY_RIG`, `MY_ANTENNA` and `TX_PWR` the client sends are kept. Missing `DXCC`, `CQZ`, `ITUZ` and
`CONT` are filled from the reference data as on the native API, after the ID
is derived, so a resend keeps its ID when the reference data changes.

The body carries no UUID, so the QSO's ID is derived from the converted record
the way an ADIF import derives it, also including the Station UUID in the hash.
Identical contacts at different Stations have different IDs. Station names,
callsigns and defaults are not part of that Station identity, so changing them
does not change how a resend is recognized. A new QSO is `201`:

```json
{ "data": { "id": 1291, "uuid": "019a0b2c-..." }, "meta": { "resource": "qso", "method": "POST" } }
```

`id` is the QSO's `seq`, the number `since_id` counts. Sending the same body
again, after a lost answer or after the QSO was deleted, creates nothing and is
answered as Wavelog answers a duplicate:

```json
{ "error": { "code": "validation_error", "message": "Duplicate QSO",
  "details": { "critical": [], "validation": [], "duplicate": ["JA1XYZ 20261020 094127 40m CW"] } } }
```

A QSO that only looks like an earlier one (same call, band and mode within 15
minutes) is still created.

## Lookup

`GET lookup?callsign=<call>&detail=basic` answers what the reference data and
the Logbook know about a callsign. `detail` may be left out; other details are
`400`. `station_ids` narrows the earlier QSOs to those Stations before paging.
The lookup searches across all matching live QSOs for each field's newest
nonempty value; it does not stop after the first page of history. It is the
native lookup (see [api.md](api.md)) in Wavelog's shape.

| Key | Source |
| --- | --- |
| `callsign` | The callsign, upper case |
| `dxcc`, `dxcc_lat`, `dxcc_long`, `dxcc_cqz`, `dxcc_ituz`, `cont` | The entity `cty.dat` resolves the callsign to, with the overrides of the matching alias; longitude grows towards the east |
| `dxcc_id` | The entity's ADIF code from `cty.csv` |
| `name`, `gridsquare`, `location`, `state`, `us_county`, `iota_ref`, `qsl_manager` | `NAME`, `GRIDSQUARE`, `QTH`, `STATE`, `CNTY`, `IOTA`, `QSL_VIA` of the newest earlier QSO with the same base call that has the field |
| `workedBefore` | Whether there is such a QSO |

A value nothing provides is `null`, including the entity while `cty.dat` is not
installed.

## Catalog

`GET catalog?topic=contest` lists the distinct `CONTEST_ID`s of the Logbook's
live QSOs, ignoring case, as `{"contest": "<id>", "name": null}`. There is no
contest table, so there are no names.

`GET catalog?topic=subdivisions&dxcc=<code>` lists the subdivisions of an
entity from the ADIF table built into the server, as
`{"dxcc": 339, "state": "10", "name": "Tokyo"}` ordered by `state`, without
the subdivisions the specification marks deleted or import-only. An entity
without subdivisions is an empty list, `dxcc` is required, and a `dxcc` that
is not an ADIF DXCC entity code is `404`.

`GET catalog` without a topic answers `{"topics": ["contest", "subdivisions"]}`
in `data`. Another topic is `400 validation_error` with those names in
`details.allowed`.

## Correspondence with Wavelog API v2

How each part of Wavelog's API v2, as its documentation
(<https://docs.wavelog.org/developer/api-v2/>) described it on 2026-10-23,
maps onto this layer. "Yes" is served as described above, "Partly" is served
with the differences noted, and "No" is not served: an unknown path is `404
not_found`, a method a known path does not serve is `405` without a body, and
an unsupported parameter value is `400 validation_error`. Query parameters this layer does not know are ignored.
Wavelog scopes are not modelled; a `wl2` token may use everything here.

| Wavelog API v2 | Here | Notes |
| --- | --- | --- |
| `GET /api/v2`, `/api/v2/status` | No | No client uses the status check |
| `GET token` | No | Token metadata belongs to the native API (`GET /api/tokens`) |
| `GET station` | Partly | Only Stations with a Wavelog ID that are not archived. `active` is always `false` |
| `GET station/{id}`, `POST`, `PATCH`, `DELETE station` | No | Stations are managed by owners through the native API and the CLI |
| `GET qso?format=adif` | Partly | Insertion order by `seq`. `per_page` defaults to 1000. `qsl_filter` refuses `qrz` and `clublog`. `limit` is ignored |
| `GET qso?callsign_match=plain` | Yes | Not in Wavelog's documentation; an extension of the kb10uy/wavelog fork |
| `GET qso` as JSON (`format=json`, Wavelog's default) | No | `400`; ADIF is the only format the clients read |
| `GET qso/{id}`, `PATCH qso/{id}`, `DELETE qso/{id}` | No | Edits go through the native API, which checks the revision |
| `POST qso` with one JSON QSO | Partly | `freq` and `freq_rx` must be whole hertz, without a unit suffix such as `7.0475M`. `time_on` must be ADIF (`HHMM`, `HHMMSS`), not `HH:MM`. The answer is `{id, uuid}` rather than the whole QSO, with no `Location` header. A resend is a duplicate, answered as described above |
| `POST qso` in bulk (`qsos`) or as ADIF (`import_type: "adif"`, `dryrun`) | No | `400`; bulk loads go through `jl1his-logger import` or `POST /api/logbooks/{id}/imports` |
| `GET lookup?callsign=` with `detail=basic` | Partly | No `dxcc_flag`, `bearing`, `lotw_member`, `suffix_slash`, or `meta.date`. `band`, `mode`, `callbook` and `date` are ignored. A `station_ids` entry outside the Logbook is `403`, where Wavelog ignores it |
| `GET lookup?callsign=` with `detail=full` | No | `400`; the worked and confirmed flags per band and mode are not computed |
| `GET lookup?grid=` | No | `400` (`callsign` is required) |
| `GET catalog` (no topic) | Yes | Lists only the topics served here |
| `GET catalog?topic=contest` | Partly | `CONTEST_ID`s found in the Logbook's QSOs, with no `id` and a `null` `name`; there is no contest table |
| `GET catalog?topic=subdivisions` | Yes | From the ADIF table built into the server; each item also carries `dxcc`. `404` for a code that is not an ADIF DXCC entity |
| `GET catalog?topic=dxcc` | No | `400`; could be built from the installed `cty` data if a client needs it |
| `logbook` | No | Logbooks are the native API's; a `wl2` token is fixed to one |
| `radio` | No | CAT is not part of this application |
| `statistic` | No | Dashboards are not part of this application |
| `confirmation` | No | QSL state is read from the QSO's ADIF fields |
| `contest` | No | There is no contest table |
| `club`, `clubstation` | No | Club stations are Logbooks with Memberships |
| API v1 (`/api/qso` with the key in the body, `/api/station_info/{key}` and the rest) | No | Not served |
